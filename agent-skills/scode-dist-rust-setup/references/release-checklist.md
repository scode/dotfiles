# Releasing (CONTRIBUTING.md Section)

Use this section as the baseline for the `## Releasing` heading in `CONTRIBUTING.md`, with `<crate_name>` replaced by
the tool's name. On a new repository, copy it as is. On a repository that already has a Releasing section, change only
the steps the push model touched (the release watch step and the hand-off step at the end, and the preflight items about
`tap`, `publish-jobs`, secrets, and the archive contract) and keep every repository-local item already there, such as
saltybox's `allow-dirty` and permission-hardening rules. The section is written as agent-centric instructions so that
when a user says "cut a release", an agent can guide them through the entire flow, including the final hand-off of the
tag to the Homebrew tap, which nothing automatic does any more.

---

## Releasing

Ask the user what version to bump to. Read the current version from `Cargo.toml`, then offer three options showing the
resulting version for each:

- Bump bugfix (e.g. 0.1.0 → 0.1.1)
- Bump minor, reset bugfix (e.g. 0.1.1 → 0.2.0)
- Bump major, reset minor+bugfix (e.g. 0.2.0 → 1.0.0)

Then proceed:

1. Ensure you're on a fresh main with a clean working copy: `gt sync --all`, `gt checkout main`, then verify
   `git status` shows no uncommitted or untracked changes. Abort if dirty.
2. Set the version in `Cargo.toml`.
3. Refresh the lockfile: `cargo update --workspace`
4. Validate lockfile consistency: `cargo metadata --format-version 1 --locked > /dev/null`
5. Generate the changelog and insert any custom release notes:
   1. Run `git-cliff --tag "v$VERSION" -o CHANGELOG.md`
   2. Ask the user if they want to add custom release notes. Tell them to create `release-notes/$VERSION.md` and confirm
      when ready (or decline to skip). If the file exists, insert its contents into `CHANGELOG.md` immediately after the
      `## [$VERSION]` heading line (before the first `###` group)
6. Run `dprint fmt` to fix any formatting issues in the generated changelog.
7. Verify the changelog heading exists: `rg -n "^## \[$VERSION\]" CHANGELOG.md`
8. Create a release PR with commit message `chore: release $VERSION`. The PR must include `Cargo.toml`, `Cargo.lock`,
   and `CHANGELOG.md` (CHANGELOG.md will be untracked on first release — `gt add` it before committing).
9. **Stop and explicitly ask the user for confirmation before merging and tagging.** Do not silently wait — tell the
   user you are ready to merge and tag, and ask them to confirm.
10. Merge the PR: `gh pr merge <number> --squash`
11. Sync and checkout main: `gt sync --all`, `gt checkout main`.
12. Tag the merge commit and push: `git tag v$VERSION && git push origin v$VERSION`
13. Watch the Release workflow: `gh run watch <run-id>`. Confirm it succeeds (dist plan, release-plan tests, artifact
    builds) and that the GitHub release has the four `<crate_name>-<target>.tar.xz` archives attached.
14. Hand the new tag to the Homebrew tap. The release workflow does not publish a formula; `scode/homebrew-dist-tap`
    pulls a chosen tag and generates the formula itself, behind human review. Tell the user the tag is ready for a tap
    update (`cargo xtask update <crate_name> --tag v$VERSION` in the tap repository, followed by the routine update
    checklist in the tap's `docs/pull-workflow.md`, which is the authority on what that PR must include), and that
    `brew upgrade <crate_name>` will not see the release until that tap change is merged. The tap must already have
    registered `<crate_name>`; its updater refuses unknown tools. Never re-upload or replace assets on a published tag:
    the tap records the archive hashes it accepted, and different bytes for the same tag are treated as an integrity
    error.

## Preflight Checklist (One-Time Per Repository)

1. Initialize git-cliff config if `cliff.toml` is missing:
   - `git cliff --init keepachangelog`
2. Ensure `dist-workspace.toml` has:
   - `plan-jobs = ["./release-plan-tests"]`
   - no `tap`, no `publish-jobs`, and no `homebrew` entry in `installers`. `scode/homebrew-dist-tap` pulls releases;
     nothing in this repository may push a formula.
3. Ensure `.github/workflows/release.yml` is generated by dist (`dist generate --check`, run with a dist binary of
   exactly the version pinned by `cargo-dist-version` in `dist-workspace.toml`; any other version refuses to run, and
   `dist init` would silently rewrite the pin) and uses no secret other than `GITHUB_TOKEN`. If `dist-workspace.toml`
   has `allow-dirty = ["ci"]`, `--check` passes regardless; confirm the workflow by reading it instead.
4. Ensure `.github/workflows/conventional-commit-pr-title.yml` exists.
5. Ensure `cliff.toml` exists and is configured for Conventional Commit parsing.
6. Confirm the archive contract the tap depends on is intact: `targets` in `dist-workspace.toml` is still exactly
   `aarch64-apple-darwin`, `aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`, and
   `dist plan` lists one `<crate_name>-<target>.tar.xz` per target containing only `README.md`, `CHANGELOG.md`,
   `LICENSE`, and the `<crate_name>` binary. The tap's updater validates against this and has no fallback, so any change
   here needs a coordinated change in the tap.
